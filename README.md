学生公寓管理系统需求分析说明
一、系统目标

本系统的主要目标是设计并实现一个功能较完整的学生公寓管理系统，实现对学生住宿相关信息的集中管理。

具体目标如下：

实现学生、公寓管理员、公寓楼、房间等基础信息的管理。
实现学生住宿分配、换宿、退宿等住宿管理功能。
实现学生维修申报、公寓管理员处理维修申请等维修管理功能。
实现访客登记与查询功能，方便公寓安全管理。
实现公告发布、文件上传、图片上传、视频上传等信息发布功能。
实现不同角色的权限控制，保证不同用户只能访问对应功能。
通过数据库存储过程、函数、事务和触发器提高系统数据处理能力和数据一致性。
形成完整的数据库设计文档、ER 图、数据库表结构和系统实现说明。
三、系统用户角色分析

系统主要包含三类用户：系统管理员、公寓管理员和学生。

1. 系统管理员

系统管理员拥有系统最高权限，主要负责维护系统基础数据和整体运行状态。

主要职责包括：

管理学生信息；
管理公寓管理员信息；
管理公寓楼信息；
管理房间信息；
分配或调整学生宿舍；
查看住宿统计信息；
管理系统公告和附件；
查看系统运行日志。
2. 公寓管理员

公寓管理员主要负责具体公寓楼的日常管理工作。

主要职责包括：

查看所负责公寓楼的房间信息；
查看学生入住情况；
处理学生维修申报；
更新维修状态；
登记访客信息；
发布或管理公寓通知；
上传维修图片、处理附件等相关文件。
3. 学生

学生是系统的普通用户，主要使用与本人住宿相关的功能。

主要职责包括：

查看个人基本信息；
查看本人住宿信息；
提交维修申报；
上传维修相关图片；
查看维修处理进度；
查看公寓公告；
查看与本人相关的访客登记信息。

用户编号；
用户名；
密码；
用户角色；
关联身份编号；
账号状态；

用户角色包括系统管理员、公寓管理员和学生。系统根据用户角色控制其可访问的功能模块。

2. 学生数据

学生数据用于记录学生基本信息和住宿状态。

主要包括：

学生编号；
学号；
姓名；
性别；
学院；
专业；
班级；
联系电话；
邮箱；
入住状态。

学生信息是住宿分配、维修申报和访客登记等功能的基础数据。

3. 公寓管理员数据

公寓管理员数据用于记录负责公寓管理的工作人员信息。

工号；

工作状态。

五、功能需求分析

本系统主要分为登录与权限管理、基础信息管理、住宿管理、维修管理、访客管理、公告文件管理和统计管理等功能模块。

5.1 登录与权限管理模块

该模块用于完成用户身份认证和权限控制。

主要功能包括：

用户登录；
用户退出；
根据用户角色进入不同首页；
修改密码；
权限控制；
禁用或启用账号。

系统需要根据用户角色区分功能权限。例如，学生只能查看本人住宿信息和提交维修申报；公寓管理员只能管理其负责公寓的相关事务；系统管理员可以管理所有基础信息。

5.2 学生信息管理模块

该模块主要面向系统管理员。

主要功能包括：

新增学生信息；
修改学生信息；
删除学生信息；
按学号、姓名、学院、专业、班级查询学生；
查看学生当前住宿状态；
查看学生历史住宿记录。

学生信息管理是整个系统的基础，住宿分配、维修申报和访客登记都需要使用学生数据。

5.3 公寓管理员信息管理模块

该模块主要由系统管理员使用。

主要功能包括：

新增公寓管理员；
修改公寓管理员信息；
删除或停用公寓管理员；
查询公寓管理员；
为公寓分配负责管理员。

该模块用于明确公寓楼与管理员之间的管理关系。

5.4 公寓与房间管理模块

该模块用于维护公寓楼和房间信息。

主要功能包括：

新增公寓楼；
修改公寓楼信息；
删除公寓楼信息；
新增房间；
修改房间信息；
查询房间信息；
查看房间当前入住人数；
查看房间剩余床位数；
设置房间状态。

房间状态包括正常、维修中、停用等。只有状态为正常且有剩余床位的房间才能进行住宿分配。

5.5 住宿分配管理模块

该模块是系统的核心业务模块之一。

主要功能包括：

为学生分配宿舍；
学生换宿；
学生退宿；
查看当前住宿记录；
查看历史住宿记录；
查询某房间的入住学生；
查询某学生的住宿历史。

业务规则如下：

一个学生同一时间只能有一条“入住中”的住宿记录。
房间当前入住人数不能超过最大容量。
分配宿舍时，需要更新住宿记录和房间当前入住人数。
换宿时，需要结束原住宿记录，新增新住宿记录，并同步更新原房间和新房间的人数。
退宿时，需要更新住宿记录状态，并减少房间当前入住人数。

该模块适合使用数据库事务保证数据一致性。

5.6 维修申报管理模块

该模块用于处理学生宿舍中的设备损坏、门窗故障、水电问题等维修需求。

学生端功能包括：

提交维修申请；
填写维修类型；
填写问题描述；
上传故障图片；
查看维修状态；
查看维修处理结果。

公寓管理员端功能包括：

查看待处理维修申请；
受理维修申请；
更新维修状态；
填写处理说明；
上传维修结果附件或图片；
完成维修申请。

维修状态包括：

待处理；
处理中；
已完成；
已取消。

该模块可以体现图片上传和文件管理功能。例如，学生提交维修申请时可以上传故障图片，管理员处理完成后可以上传维修结果图片或处理附件。

5.7 访客登记管理模块

该模块用于记录外来人员进入学生公寓的情况。

主要功能包括：

新增访客登记；
记录访客姓名、联系电话、证件号码；
选择被访问学生；
记录被访问房间；
记录来访原因；
记录来访时间；
记录离开时间；
查询历史访客记录；
按学生、房间、时间段查询访客信息。

访客登记功能有助于提高公寓管理的安全性和可追溯性。

5.8 公告与文件管理模块

该模块用于发布公寓通知、管理制度、安全提示等信息。

主要功能包括：

发布公告；
修改公告；
删除公告；
查看公告；
上传公告附件；
上传宣传图片；
上传安全教育视频；
学生下载公告附件；
学生查看公寓通知。

该模块用于满足课程设计中对图片、视频、文件管理的要求。

5.9 数据统计模块

该模块用于对系统中的关键数据进行统计分析。

主要功能包括：

统计学生总数；
统计公寓总数；
统计房间总数；
统计各公寓入住人数；
统计各公寓剩余床位数；
统计维修申报数量；
统计不同维修状态的申请数量；
统计访客登记数量；
统计房间入住率。

统计结果可以通过表格或简单图表展示，方便管理员了解公寓运行情况。

5.10 系统日志模块

该模块用于记录系统中的关键操作。

主要功能包括：

记录用户登录操作；
记录新增、修改、删除数据操作；
记录宿舍分配操作；
记录维修处理操作；
记录公告发布操作；
查询系统日志。

系统日志有助于后期维护和异常排查。

六、业务流程分析
6.1 用户登录流程
用户进入登录页面。
输入用户名和密码。
系统验证用户名和密码是否正确。
验证成功后，系统判断用户角色。
根据角色进入对应首页。
验证失败时，系统提示用户名或密码错误。
6.2 学生住宿分配流程
管理员进入住宿分配页面。
选择需要分配宿舍的学生。
系统查询当前可用房间。
管理员选择目标房间和床位。
系统判断房间是否有剩余床位。
若满足条件，系统生成住宿记录。
系统更新房间当前入住人数。
系统更新学生入住状态。
6.3 学生换宿流程
管理员查询学生当前住宿信息。
管理员选择新的房间和床位。
系统检查新房间是否可用。
系统结束原住宿记录。
系统减少原房间当前入住人数。
系统新增新住宿记录。
系统增加新房间当前入住人数。
若中间任一步骤失败，整个操作回滚。
6.4 维修申报流程
学生登录系统。
学生进入维修申报页面。
填写维修类型和问题描述。
上传故障图片。
系统生成维修申报记录，状态为“待处理”。
公寓管理员查看待处理维修申请。
管理员受理申请，状态改为“处理中”。
维修完成后，管理员填写处理结果。
系统将维修状态改为“已完成”。
6.5 访客登记流程
访客到达公寓。
公寓管理员登记访客基本信息。
管理员选择被访问学生和房间。
系统保存访客来访时间和来访原因。
访客离开时，管理员填写离开时间。
系统保存完整访客记录。
6.6 公告发布流程
管理员进入公告管理页面。
填写公告标题和内容。
根据需要上传附件、图片或视频。
系统保存公告信息。
学生登录后可以查看公告并下载附件。
七、非功能需求分析
7.1 安全性需求

系统需要保证用户数据和业务数据的安全。

主要要求包括：

用户必须登录后才能访问系统；
不同角色具有不同权限；
密码不能明文显示；
普通学生不能访问其他学生的敏感信息；
删除重要数据前需要进行确认；
关键操作应写入系统日志。
7.2 完整性需求

系统需要保证数据库数据的完整性和一致性。

主要要求包括：

学号、用户名等字段不能重复；
住宿记录必须关联有效学生和有效房间；
房间当前人数不能超过最大容量；
删除学生、公寓、房间等基础数据时，应考虑关联数据；
住宿分配、换宿、退宿等操作应保证事务一致性。
7.3 可用性需求

系统界面应简单清晰，便于用户使用。

主要要求包括：

功能菜单清楚；
查询功能方便；
表单输入有必要提示；
操作成功或失败后有明确反馈；
页面布局简洁，适合课堂展示。
7.4 可维护性需求

系统应具有较好的代码结构，便于后期修改和扩展。

主要要求包括：

前端页面、后端逻辑、数据库操作分层设计；
数据库表命名规范；
字段命名清晰；
代码中添加必要注释；
SQL 文件分类保存。
7.5 扩展性需求

系统后续可以扩展更多功能，例如：

宿舍卫生检查；
水电费管理；
门禁记录；
智能报修派单；
公寓满意度评价；
数据可视化分析。
八、数据库高级功能需求

根据课程设计要求，系统需要设计合理的存储过程、函数、事务和触发器。

8.1 存储过程需求

可以设计“自动分配宿舍”存储过程。

功能描述：

系统根据学生编号、目标公寓编号和房间类型，自动查询有空余床位且状态正常的房间，并为学生生成住宿记录。

示例：

proc_assign_room(student_id, apartment_id, room_type)
8.2 函数需求

可以设计“计算房间剩余床位数”函数。

功能描述：

根据房间最大容量和当前入住人数，计算并返回该房间的剩余床位数。

示例：

func_get_available_beds(room_id)
8.3 事务需求

可以在“学生换宿”功能中使用事务。

事务内容包括：

修改原住宿记录状态；
原房间当前人数减 1；
新增新住宿记录；
新房间当前人数加 1；
更新学生住宿状态。

如果其中任意一步失败，则全部回滚。

8.4 触发器需求

可以设计“新增住宿记录后自动更新房间人数”触发器。

功能描述：

当住宿记录表新增一条状态为“入住中”的记录时，系统自动更新对应房间的当前入住人数。

也可以设计“维修状态更新后自动写入系统日志”触发器，用于记录维修处理操作。

九、主要实体及关系说明

根据系统需求，主要实体包括：

用户；
学生；
公寓管理员；
公寓；
房间；
住宿记录；
维修申报；
访客登记；
公告；
系统日志。

主要关系如下：

公寓管理员 1 —— n 公寓
公寓 1 —— n 房间
房间 1 —— n 住宿记录
学生 1 —— n 住宿记录
学生 1 —— n 维修申报
房间 1 —— n 维修申报
学生 1 —— n 访客登记
公寓管理员 1 —— n 访客登记
公寓管理员 1 —— n 公告
用户 1 —— 1 学生 / 公寓管理员

说明：

一个公寓管理员可以管理多个公寓。
一个公寓包含多个房间。
一个房间可以对应多条住宿记录，但同一时间只能入住不超过容量限制的学生。
一个学生可以有多条住宿历史记录，但同一时间只能有一条有效住宿记录。
一个学生可以提交多条维修申报。
一个房间可以产生多条维修申报。
一个学生可以对应多条访客登记记录。
一个公寓管理员可以登记多条访客记录。
一个公寓管理员可以发布多条公告。
十、系统边界说明

本系统主要面向学生公寓基础管理，不涉及复杂财务结算、真实门禁设备对接、短信通知接口等功能。

系统重点完成以下内容：
